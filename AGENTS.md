# AGENTS.md – KüchenWert Repository Knowledge

## Project Overview
- German-language kitchen (Küche) lead-gen and comparison platform, forked from a caravan auction stack
- Live domain: `kuechenwert24.de` (brand: KüchenWert)
- Supabase project ID: `gzqayoalwtmypndrmqes`
- Stack: React 18 + TypeScript + Vite 5 + Tailwind + shadcn/ui + Supabase
- **Primary product:** Funnels A/B/C + Küchenrechner + dealer marketplace. Do NOT implement new Wohnmobil/Caravan features. User-facing copy must say Küche, never Fahrzeug/Wohnmobil.
- Caravan frontend code and Edge Functions were removed or tombstoned on 2026-09-28. The caravan tables (`auctions`, `bids`, `kitchens`, `kaufchance_invitations`, `post_auction_offers`, `appointments`, `wizard_sessions`, …) still exist in the DB as unused legacy — do not build on them.

## Do
- Use React functional components with hooks
- Use TanStack React Query v5 for server state
- Use Zod for all form validation
- Use `ensureValidRLSSession()` before every RLS query
- Use `invokeWithAuth()` for all authenticated Edge Function calls
- Use shadcn/ui components from `src/components/ui/`
- Use the shared email template `_shared/email-builder.ts` for all emails
- Use `SECURITY INVOKER` for all new database functions (see exceptions below)
- Keep components small and focused (< 200 lines)
- Keep diffs small and focused on one feature
- **Session-Start Check**: First action in every new session = `git fetch origin main && git status`. If `Your branch is ahead of 'origin/main'`: stranded commits → push immediately before doing anything else (Dokploy is blocked).
- **Migration File First**: When changing the DB via `apply_migration` MCP tool, write the SQL file under `supabase/migrations/<timestamp>_<name>.sql` FIRST, then apply. The file is the source of truth — without it the change is invisible to git, fresh checkouts, and CI.
- **Edge Function periodisch → Cron in selber Migration**: If a new Edge Function is meant to run on a schedule (image processing, cleanup, digests, reminders), create the `cron.schedule(...)` call in the SAME migration that documents the function. Multiple production bugs (e.g. `process-photo` 2081 unprocessed photos) came from "function exists but cron was forgotten".
- **ALWAYS work directly on `main` and push after every commit** (`git push origin main`)
  - Dokploy auto-deploys ONLY from `main` — feature/fix branches do NOT trigger deploys
  - If a tool/CI auto-creates a feature branch (e.g. `cursor/*`), immediately fast-forward merge to `main` and push: `git checkout main && git merge --ff-only <branch> && git push origin main`
  - Before every push: `git fetch origin main` to detect concurrent agents/devs. If diverged: `git pull --rebase origin main` then push.

## Don't
- Do NOT call React Hooks after an early return
- Do NOT use `getSession()` directly for RLS queries (returns expired tokens)
- Do NOT access `profiles.role` (does not exist – use `user_roles` table)
- Do NOT use `verify_jwt: true` for Edge Functions with **custom auth logic** (gateway 401 has no body — see Edge Functions section for nuances)
- Do NOT hard-code colors – use Tailwind classes
- Do NOT add new heavy dependencies without checking existing alternatives
- Do NOT use `rm -rf` on project directories
- Do NOT use `git push --force`
- Do NOT leave commits stranded on a feature/fix branch — Dokploy only deploys from `main`. Always fast-forward into `main` and push there.
- Do NOT push without first running `git fetch origin main` — concurrent agents may have pushed; surprise divergence wastes a deploy slot
- Do NOT add new tables to the `supabase_realtime` publication unless a frontend component actually subscribes to them. Each table in the publication writes to WAL for every change → measurable load.
- Do NOT call `supabase.storage.from(...).upload(file)` without `cacheControl` — see "Storage Uploads" section
- Do NOT apply a migration via MCP without also writing the file to `supabase/migrations/` first

## Commit Checklist
Before every commit:
1. `npm run typecheck` and `npx tsc --noEmit -p tsconfig.app.json` – all green (the root `tsconfig.json` only holds references, plain `npx tsc --noEmit` checks nothing)
2. `npx eslint --fix` on changed files – no errors
3. `npm run build` – successful production build
4. Diff is small and focused on one feature/fix
5. Update the TODO list in `project.md` (mark completed tasks)
6. Commit message format: `feat(scope): short description` or `fix(scope): short description`
7. **Verify you are on `main`**: `git branch --show-current` MUST print `main`. If not, switch first (`git checkout main`) — never commit on `cursor/*` or other feature branches because Dokploy will not deploy them.
8. **`git fetch origin main` BEFORE pushing**: detects concurrent commits from parallel agents/devs. If diverged: `git pull --rebase origin main` first.
9. **IMMEDIATELY push to GitHub**: `git push origin main` (MANDATORY – local-only commits are NOT acceptable)
10. If push fails: `git pull --rebase origin main && git push origin main`
11. Verify push: `git status` must show `Your branch is up to date with 'origin/main'`. The push starts `.github/workflows/deploy.yml` (typecheck, lint, tests, build, then Dokploy deploy via API); production is updated a few minutes later. Check the run with `gh run list --workflow deploy.yml` and the live build via `last-modified` of `/`.
12. If the change applied a DB migration via MCP: confirm the corresponding `supabase/migrations/<timestamp>_<name>.sql` file exists AND is part of the commit. Migration without file = invisible to git = unreproducible.

## Good Examples (copy these patterns)
- **Functional component with hooks**: `src/features/account/EmailPreferencesCard.tsx`
- **Form with Zod validation**: `src/features/marketplace/components/ContactComplaintCard.tsx`
- **Edge Function with error handling**: `supabase/functions/kw-contact/index.ts` (Zod, Turnstile, rate limit, specific HTTP codes)
- **Authenticated API call**: `src/lib/sessionGuard.ts` (`invokeWithAuth`)
- **Realtime subscription**: `src/components/NotificationCenter.tsx` (filtered by `user_id`)

## Bad Examples (avoid these patterns)
- **Class-based components**: None currently, but do not introduce them
- **Direct getSession() for RLS**: Any code using `supabase.auth.getSession()` before RLS queries without `ensureValidRLSSession()`
- **God components**: Components over 300 lines – split into smaller sub-components
- **Storage upload without `cacheControl`**: Any `.upload(path, file)` call missing the `cacheControl: "31536000, immutable"` option — defaults to 1h cache and breaks edge caching
- **Edge Function without Cron when periodic**: Deploying a function intended to run on a schedule without also adding the `cron.schedule(...)` migration in the same commit
- **MCP migration without file**: Calling `apply_migration` without writing `supabase/migrations/<timestamp>_<name>.sql` first
- **Migration committed but never applied**: A `.sql` file in `supabase/migrations/` that is NOT listed in `supabase_migrations.schema_migrations` is dead code that silently does nothing. Real example: 2026-04-21 the cron-throttle file was committed (commit `210d723`) but never applied → photo crons ran 5× too fast for 16 h and overloaded the connection pool. **After every `apply_migration` call, verify with `select 1 from supabase_migrations.schema_migrations where version = '<ts>';`**. The Schedule-Drift card on `/admin/cron-health` will surface this class of bug for cron jobs going forward.
- **Global Realtime listener**: `supabase.channel("foo").on("postgres_changes", { event: "*", table: "bids" }, ...)` without a `filter` — broadcasts every change in the table to every client

## Key Architecture Patterns

### Design system (contrast & consistency)
- Colors only via tokens in `src/index.css` (warm cream + Forest Sage + anthracite). No hard-coded Tailwind palette colors for surfaces or text (`PageHero` and the auth pages use `from-primary/[0.08] via-background`). Dark bands (header top bar, footer) use `bg-secondary` / `bg-secondary-dark` with `text-white/70`+.
- Contrast (WCAG 2.2 AA, measured with axe on all public pages, desktop + mobile): `text-muted-foreground` ≥ 4.8:1 even on `bg-muted`; never fade text with opacity (`/50`–`/80`). Error text `text-destructive`, status text `text-success` / `text-warning` (all AA on cream and muted). `--accent` (brass) only for tints, badges and decorative icons: as text or with white text it fails AA.
- Form controls: borders and the off-track of switches use `--input` (≥ 3:1, WCAG 1.4.11); `--border` is only for decorative lines and cards. Unselected checkboxes/radios/indicators use `border-input`.
- Links inside running text use `.link-inline` (underlined, WCAG 1.4.1); standalone links and navigation don't need it.
- Shapes: buttons and form fields `rounded-xl` (Button, Input, Select, Textarea, `.btn-*`, `.input-field`), cards and dialogs `rounded-2xl`, menus/popovers `rounded-xl`, badges and chips `rounded-full`. CTAs are flat `bg-primary` (no `gradient-hero` on buttons; the gradient stays on decorative icon tiles). Funnel helpers: `.btn-primary`, `.btn-secondary`, `.btn-ghost`, `.helper-text`, `.card-clickable` (+ `.is-selected`).
- Floating buttons (WhatsApp bottom left, scroll-to-top bottom right; both `h-12 rounded-xl` at `bottom-[calc(2rem+env(safe-area-inset-bottom))]`): below `2xl` the footer bottom bar keeps `pb-[calc(6rem+env(safe-area-inset-bottom))]`, otherwise they cover Impressum and Barrierefreiheit at the end of the page. New fixed elements at the bottom need the same clearance.
- Before shipping UI changes, check mobile overflow (390 px) – a `flex` paragraph with text and links once made the Funnel C contact step 446 px wide.

### Funnels & Leads
- Funnel A `/formular` (question flow, submit via `kw-lead`), Funnel B `/funnel/b` (`kw-lead-b`), Funnel C `/funnel/c` (planner with room photo, AI render and price engine via `kw-planner`).
- **Funnel C: every visualization is a lead.** Steps in `src/features/planner/flow.ts` (one question per screen: form, walls (ceiling height optional behind „Raumhöhe angeben“), photo, style … `abluft` (Abluft/Umluft, detail step) … PLZ). „Küche visualisieren“ on the PLZ step starts the render in the background and shows the spinner step `visualisierung` (at least 4.5 s), then `angebote` („Ja“ = consent `share_with_studios`, text version `kw-projekt-2026-09-30`), `zeitrahmen`, `budget`, `anlass`, `wohnsituation` (only with Ja; the budget question has no price anchor, because no estimate may appear before the lead), `name`, `kontakt` (name, e-mail and phone required) and finally `ergebnis` with render, price and variants. No amount and no render appear before that: `kw-planner` returns image URLs (`status`, `session`) and estimates (`generate`, `save`, `session`) only once `planner_sessions.lead_id` is set, and allows at most 3 renders before the lead (`contact_required`). „Nein“ creates a lead without tender (share consent `false`); `kw_open_tender` refuses such leads on every path, admins included. Customers request offers later in the result (`kw-planner` `request-offers`) or on `/projekt` (`kw-project` `request-offers`), both via `_shared/planner-offers.ts`, which also re-enqueues `project_created`. Without a tender the worker mails „Ihre Küchenvisualisierung & Preisschätzung“ and the admin „Neuer Lead (nur Visualisierung)“. The browser still computes the estimate with the public rate card (`usePriceModel()`), so shown and stored prices match; `src/features/planner/__tests__/lead-gate.test.tsx` checks that no step before the result shows an amount (except the fixed scale of the budget question, which must not show anything from the estimate) or the render. The planner state (`kw_planner_v2`) keeps a submitted planning as result until „Neue Küche planen“; old step ids (`raum`, `ausstattung`, `kontakt`) are mapped on load.
- **Studios must not mistake defaults for customer wishes.** The planner starts with preset values (configuration and example wall lengths). The browser records answered steps and typed walls (`answered` in the planner state, sent with `save`/`generate` into `planner_sessions.provenance`, logic in `_shared/planner-provenance.ts`). `_shared/planner-summary.ts` builds the tender summary: `defaults` marks rows from skipped steps („Standard“ in portal and studio mail, never in the customer mail), `room.dimensions_source` marks untouched example walls (portal, studio mail, DXF header; such leads do not count as `p_has_dimensions`). The summary also carries timeframe, sink and tap, and with „Ja“ budget, occasion and housing. Plannings without provenance (browser state from before) stay unmarked. The ceiling height is optional, so `ceilingHeightCm` stays null unless the customer typed it (values outside 200–400 cm are dropped, never clamped). The budget slider (`BudgetSliderStep`, prop `confirmed`) starts as „Ihr Budget?“ with nothing selected: Funnel A counts the budget only after the customer moved the slider, tapped an amount or chose „Weiß ich nicht“ (`budget_confirmed`); untouched it is stored as `budget_source: default` without `budget_midpoint`. Funnel C sends a budget only from the `budget` step (`budget_source` `slider` or `unknown`), and its `budget_midpoint` is that stated budget, never the estimate. Funnel A asks „Was soll das Küchenstudio übernehmen?“ (`leistungen`, `services`, optional): without an answer the estimate assumes delivery and assembly, but only real answers are stored and shown to studios. `kw_lead_public_summary` passes the Funnel B payment terms (financing, APR, months, down payment), waste separation (older leads; now the extra `abfallsystem`), what the offer includes (`offerIncludes`, same keys as `lead_bids.includes`) and until when it is valid (`offerValidUntil`) to studios (`describeFunnelB`).
- Funnel B starts with the existing offer: price plus documents (categories `angebot`, `grundriss` = planning, `kueche_bild` = photos; up to 10 files à 20 MB, PDF or image) or "später nachreichen". Steps in `src/features/funnel-b/steps.ts` (`?schritt=<key>`): price (plus optional „Angebot gültig bis“, checked in browser and `kw-lead-b` with `plausibleOfferDate`) → „Was ist in diesem Preis enthalten?“ (`leistungsumfang`) → documents now/later → upload (only „now“) → Küchenform → timeframe → „Details angeben?“ (only „Ja“ shows brand … extras (incl. Mülltrennsystem) … down payment, each with „Details überspringen“) → PLZ → name → contact → consents; old links `?schritt=muell`/`lieferung` land on `extras`/`zahlung`; steps after the offer redirect to it until price and documents are complete. Upload logic for both functions lives in `_shared/lead-files.ts` (announce → signed upload URLs → attach with content check and EXIF stripping); browser side in `src/features/funnel-b/`. Customers of all funnels add documents later on `/projekt/:token` (Funnel A/C ask for floor plan and room photos, `leadFileCategoriesFor`; `kw-project` `upload-files` / `attach-files`, max. 20 per project, until the tender is closed), which enqueues `lead_files_added` → admin mail.
- **Studios see customer documents only when released:** an admin checks each file in the tender panel and sets `lead_files.shared_with_studios` (only if no names or contact data are visible, otherwise upload a redacted version and release that one), or after the studio bought the contact / won the project (then all files). Enforced by the storage policy `LeadFiles: dealer read released` → `kw_can_view_lead_file()` and by `kw_dealer_project` (`media` items with `kind: "document"`, file names hidden before purchase). This mirrors the Funnel B consent (`kw-unterbieten-2026-09-28b`). All submits: Honeypot, Turnstile, rate limit, `submission_id` against duplicates, lead + `lead_consents` in one transaction. Without a valid Turnstile token a lead is stored as `bot_check = unverified` and not published automatically.
- Consumers reach their project via `/projekt/:token` (`kw-project`): token never in tracking, error or mail logs; the route is served with `no-referrer`, `noindex`, `no-store`.
- **Additions after submit (`kw_lead_details`):** customers complete their project on `/projekt/:token` („Angaben vervollständigen“, `ProjectDetailsCard`: walls of the requested form, ceiling height, room features, Abluft/Umluft, connections, consultation, note; `kw-project` `save-details` writes only `customer`; planner projects are not asked what their planning already has). The team writes the expert-check briefing in the admin tender panel (`AdminTenderBriefing`: form, manufacturer and programme, run length, what the offer includes, validity, note; RLS admin only, column `expert`). `_shared/lead-details.ts` keeps only known fields and strips contact data; the funnel answers stay untouched. Studios see both in the portal („Ergänzungen“, `describeLeadDetails`), in the briefing JSON (`additions`) and in the DXF (customer walls when there is no planning). Changes and file releases enqueue `project_updated` (triggers) → `kw-market-worker` notifies studios with an offer or a bought contact (bell and mail, at most every 6 h per tender, nothing for cleared additions). Anonymization deletes the row, the data export (`kw_project_export`) contains it.
- **No contact data in studio-visible free text:** `_shared/contact-redaction.ts` replaces e-mail addresses, links and phone numbers with „[entfernt]“ before storing planner wishes and studio notes (`kw-planner`), Funnel B free texts (`kw-lead-b`) and additions; dates, measures and prices stay. Anonymization also removes the wishes from `funnel_answers`, the planner session and the tender summary. Section 3 of the privacy policy describes additions, expert check and removal.
- **Focus mode:** `/formular` (question 1 of Funnel A), `/funnel/a/*`, `/funnel/b`, `/funnel/c` and `/funnel/danke` show no site navigation, no big footer and no floating buttons; `isFunnelPath` (`src/lib/funnelRoutes.ts`) hides the WhatsApp button and skips the service-worker reload mid-funnel. Height breakpoints in `tailwind.config.ts` (`short` ≤ 699 px, `xshort` ≤ 599 px, `tall` ≥ 760 px) flatten image tiles and hide hints; option tiles pick their columns from the option count (`CardStep`, `ImageCardStep`, `MultiCardStep`; `compact` for ≥ 8 options). Funnel A asks name and contact on two screens. `tests/e2e/funnel-fit.spec.ts` checks every step of all three funnels at 375 × 548, 390 × 664 and 1366 × 657 (kw-planner mocked, no renders or leads): run it after UI changes to a funnel.
- **Homepage:** the hero (`src/components/Hero.tsx`) shows the three funnel buttons (planner featured, offers, beat an offer) without scrolling on every device from 375 × 548 up (compact H1 on phones, `short:lg:` sizes on low laptops, site header `h-16` below lg); the WhatsApp bubble appears there only after 240 px of scrolling, because it would cover the third button.
- Funnel A (→ `/projekt`) and Funnel C (result in the planner) do not land on `/funnel/danke`, so they send a virtual page view `/funnel/danke?funnel=a|c` after a lead (`src/lib/funnelThankYou.ts`): the remarketing lists recognize requests by that URL.
- **Funnel telemetry (only with statistics consent, as the privacy policy promises):** `useFunnelTelemetry` logs step changes, next/back, validation failures with field keys, field focus/blur/corrections, idle (25 s), tab switches, scroll depth, leaving (sendBeacon), JS errors, rage clicks (3 clicks on the same element within 1 s: visible button/link text, never `aria-label`, which can carry file names; non-clickable targets only by tag), exit dialog and phone clicks. Field keys come from `data-track`, `name` or `id` inside `[data-funnel-telemetry]`, never values; honeypots (`tabindex=-1`) are skipped. `src/lib/funnelTelemetry.ts` buffers until the cookie decision, drops the buffer on refusal and sends batches to `kw-funnel-telemetry` (validation in `_shared/funnel-telemetry.ts`, shared with the browser; origin check, rate limit on a hashed IP) → `kw_funnel_events` (admin read only, 90 days via `kw_retention_cleanup`). Evaluation: Admin → Analytics → Funnels (`kw_admin_funnel_stats`: reached, drop-offs, median time per step, missing required fields, field friction, devices, sources, JS errors). New event types need an entry in `FUNNEL_TELEMETRY_EVENTS` and a redeploy of `kw-funnel-telemetry` (it drops events it does not know). The first answer of a run also sends `funnel_start` (GA4) and Meta `InitiateCheckout`.
- **UX alerts (Admin → UX-Alerts, `/admin/ux`):** `kw_ux_detect_alerts()` (cron `kw-ux-alerts` hourly at :20, button „Jetzt prüfen“) turns `kw_funnel_events`, funnel-page rows of `error_logs`, `planner_renders` and `planner_sessions` into rows of `kw_ux_alerts` with severity, affected step/field, finding and a „Was tun?“ hint. Kaputt (24 h): JS errors (≥ 2 runs), failed submits (≥ 1), rage clicks (≥ 2), error-log entries, failing AI renders. Abbruch (7 days): steps with many drop-offs or clearly more than in the 4 weeks before, planner sessions with a finished render but no request (all visitors, sessions older than 2 h), runs without any request. Reibung (7 days): missing required fields, fields left empty or corrected, idle, back, exit dialog, slow steps. Rates count from 3 cases and use the lower bound of the 95 % Wilson interval (`kw_wilson_lower`), field keys are shown as names via `kw_ux_field_label` (add new field keys there). „Erledigt“ hides an alert for its window (24 h or 7 days); after that it only returns if the problem shows up again in post-fix data. Alerts not detected for 24 h close themselves. Admins read and set the status only (column grant); the sidebar and bell count open critical/warning alerts. New rule = new block in the function (migration), keep the thresholds sample-safe.

### Funnel C: AI visualization & learning price engine
- **Models are data, not code:** `kw_ai_settings` (single row, admin page `/admin/ki`) picks main, variant, fallback and challenger models plus the daily render cap (0 = paused). Only models listed in `_shared/fal-models.ts` (registry with vendor, estimated cost and the fal input per model family) are accepted; unknown IDs fall back to the defaults. IDs keep fal's vendor prefix (`fal-ai/…`, `openai/gpt-image-2.5/sunburst/edit`). The old secrets `FAL_EDIT_MODEL`, `FAL_TEXT_MODEL`, `KW_DAILY_RENDER_CAP` are no longer read. Adding a model = registry entry (verify its input schema at `https://fal.ai/api/openapi/queue/openapi.json?endpoint_id=<id>`) + test.
- **fal keeps as little as possible:** `falSubmit` sends `X-Fal-Store-IO: 0` (no request history with customer wishes) and `X-Fal-Object-Lifecycle-Preference` (generated images expire after 1 h instead of ≥ 7 days on public CDN URLs). `kw-planner` copies every result into the private bucket right away, so never raise the expiry to keep images at fal.
- **Fallback chain:** `kw-planner` moves to the next model when submit/status/result fails, the fal queue waits > 45 s (the queued job is cancelled) or processing takes > 150 s (`fallbackReason`), at most 3 attempts (`nextFallback`, `planner_renders.attempt`). Default with photo: Nano Banana Pro → Nano Banana 2 (sister model, keeps the room; covers capacity problems of one model) → FLUX.2 Pro Edit (other vendor, but redesigns the room more freely; covers Google outages and refused photos). Text: FLUX.2 Pro → Nano Banana 2. `fallback_from` holds the first model, `fallback_reason` the last error; the switch is a conditional update on (`model_slug`, `attempt`), so parallel polls never submit twice. All models run through one fal account: a locked account (no credit, invalid key) stops the whole chain, which the health alert `fal_account_blocked` reports.
- **Renders finish without the browser:** `advanceRender` serves both the browser poll (`status`) and cron `kw-planner-sweep` (every minute, only when a render is pending > 75 s; action `sweep`, cron secret). A result that fal finished is stored even after the 5-minute limit (it is paid for). When a render finishes after the tender opened without a cover, `fillTenderCover` adds it. `submit` starts a render when none succeeded or is pending (pre-lead render failed or not allowed).
- **Render budget:** the daily cap counts all renders; unverified visitors (before the lead, or lead with `bot_check = unverified`) share at most 70 % of it (`planner_renders.verified`, `OPEN_POOL_SHARE`), so bots cannot use up the renders of real customers. Pre-lead renders beyond that answer `render_after_contact` and start after the submit.
- **Variants** (`generate` with `base_render_id` + `variant_hint`) edit the selected finished render with `buildVariantPrompt` instead of re-planning from the photo, so only the requested change happens. The frontend only sends a base render while its planning key (`plannerRenderKey`: config and room without studio notes, plus photo) matches the current planning; otherwise it shows "Neu visualisieren".
- **Measure everything:** each render stores model, estimated `cost_cents`, `generation_ms` of its own attempt, the prompt version (`spec_snapshot.prompt_version`, `PROMPT_VERSION` in `_shared/kitchen-prompt.ts`) and the customer rating (`feedback`, with `feedback_reasons` on a thumbs down, IDs in `_shared/render-feedback.ts` and a CHECK). A/B groups (`planner_sessions.ai_group`, fixed per session from the UUID) compare a challenger model on photo sessions; the challenger group renders every photo image including variants with the challenger. Since the lead gate the model cannot change the lead rate, so the A/B verdict uses first-render ratings with 95 % Wilson intervals (`src/features/ai-admin/stats.ts`), fallback rate, duration and cost. `kw_admin_ai_stats` (admin RPC, max. 30 days because sessions without lead are deleted after 30 days) feeds `/admin/ki`; both it and the nightly rollup use `kw_ai_stats_between(from, to)`. Cron `kw-ai-stats-daily` (01:10 UTC, plain SQL) writes the last two Berlin calendar days into `kw_ai_stats_daily` (counts, durations, costs and model names only, kept beyond the 30-day deletion; card „Verlauf“). Every change to `kw_ai_settings` lands in `kw_ai_settings_history` (trigger, `{column: {from, to}}`). Renders finished by the sweep keep `generation_ms` null, because nobody knows when fal finished. Frontend events `planner_render` and `planner_feedback`. Health alerts: `render_cap_near` (≥ 80 % of the cap), `renders_failing`, `renders_fallback_high` (≥ 25 % fell back in 24 h), `renders_stuck` (pending > 10 min: sweep not running), `fal_account_blocked`.
- **Prompts aim at a real photo:** true-to-scale German kitchen dimensions, keep exposure, white balance, floor and wall finishes of the customer photo, nothing in front of windows, doors or radiators, no "3D render" look. Bump `PROMPT_VERSION` with every prompt change so ratings can be compared per version. Every render shown to customers or studios carries the visible `AiBadge` („KI-Visualisierung“), the result adds that studios plan dimensions on site.
- **Own model roadmap:** training data are only customer room photos with the optional consent `ai_training` (checkbox in the planner result when a photo exists, toggle on `/projekt/:token`). `_shared/ai-training.ts` copies them without contact data or free text into the private bucket `ai-training` (`kw_ai_training_samples`, 36 months, deleted on revocation, customer erasure and expiry). **Never train on renders of third-party models** (Google and OpenAI forbid using outputs for competing models; check any other vendor's terms first) — renders are not stored as training data. Next steps: use the consented photos as a fixed test set (from about 50) so new models and prompts are compared on the same real rooms before customers see them; collect photos of finished kitchens, because an edit LoRA needs before/after pairs; then train a LoRA on an open model (Qwen Image Edit Plus is in the registry and LoRA-ready via `kw_ai_settings.lora_url`), run it as challenger, promote it when it wins.
- **Learning price engine:** `kw-maintenance` task `price-calibration` (cron `kw-price-calibration`, 03:40 UTC, also a button on `/admin/ki`) re-estimates every tender with offers using the current engine and rate card (no feedback loop), compares with the median offer (`kw_price_observations`) and writes shrunk multipliers per segment (global → funnel a/c → quality (planner only) → PLZ region) to `kitchen_price_calibration` (`_shared/price-calibration.ts`, prior 8, total factor clamped to 0.7–1.45). Each tender counts with `observationWeight`: recency (half-life 365 days) × n/(n+1) for n offers, so a single offer counts half and one studio cannot move its region alone. Final order values are deliberately not used: the order scope drifts from the planning, the offers price the same planning. `kw_ai_settings.price_calibration_enabled` = false writes factor 1 everywhere (pure rate card) while learning continues. Every run is logged in `kitchen_price_calibration_runs` with the factors and the accuracy (`_shared/price-accuracy.ts`: median absolute deviation, share of offer medians inside the shown range, bias) of the estimate customers saw (`lead_auctions.estimate_*`, the honest number) and of today's engine without and with calibration (in-sample). `loadRateCard` returns card + calibration for `kw-planner`/`kw-lead`; the browser uses the same via `usePriceModel()`, so shown and stored estimates match.

## Critical Rules (Learned from Production Bugs)

### React Hooks
- **NEVER** call React Hooks after an early return – all hooks MUST be unconditionally before any `return`
- Hooks that need loaded data → move to Child-Component, NOT parent with fallback value

### Column-Level Grants
- Tables with column-level grants reject `select('*')` (directly or as relationship embed) with **`42501 permission denied`**, including `select('*', { count: 'exact', head: true })`. Select explicit columns; for counts select a single granted column (`select("id", { count: "exact", head: true })`).
- Legacy example: `public.auctions` grants each public column individually (Migrations `20260420260000` + `20260420290100`). The frontend no longer queries it; the former helper `AUCTION_PUBLIC_COLUMNS` was removed with the caravan code.

### Edge Functions
- `verify_jwt` matrix:
  - **`true`** for ADMIN-only functions that don't do their own auth (lets the Supabase gateway reject before code runs). Beware: gateway 401 has empty body — frontend errors will be opaque. Use only when frontend doesn't need to distinguish reasons.
  - **`false`** + own service-role check for functions with custom auth, public flows, or webhook signature verification. All KüchenWert functions currently fall here (`supabase/config.toml` is the source of truth).
- **Never authorize on decoded JWT claims alone.** With `verify_jwt = false` the gateway does not check signatures, so a hand-made token with `role: service_role` decodes fine. `_shared/auth.ts` verifies such tokens against the Auth server (`isGenuineServiceRoleJwt`); a function only gets that fix when it is redeployed. Probe after deploy: forged token must return 401.
- Catch-all `throw` → 500 is bad for UX. Use specific HTTP codes + readable error messages
- `supabase_deploy_edge_function` ALWAYS requires the `files` parameter with file contents
- **Deploying large functions via MCP without CLI login**: the repo is public, so pass a one-line `index.ts` that imports the function from `https://raw.githubusercontent.com/wwprojekt/kuechenwert/<full-commit-sha>/supabase/functions/<name>/index.ts`. Relative imports (`../_shared/*`) resolve against the same commit and are bundled at deploy time, no runtime dependency on GitHub. Pin a pushed commit SHA (never `main`), keep `verify_jwt` as in `config.toml`, and probe afterwards. Does not work for code that reads files via `import.meta.url`. A later CLI deploy replaces the shim with the local files.
- For periodically-running functions (cleanup, digests, reminders, outbox workers): the cron job in `cron.schedule` sends `x-kw-cron-secret` (from vault `kw_cron_secret`) and the function checks it with `checkCronOrServiceRoleOrAdmin` (`_shared/auth.ts`). Admins and the genuine service role may still call these functions manually.
- Retired functions are not deleted right away: their `index.ts` calls `serveGone("<name>")` from `_shared/gone.ts` (410 Gone) and `config.toml` lists them under "Stillgelegt". Delete them in the Supabase dashboard only after an observation period.
- Images: there is no image proxy or photo pipeline anymore. Upload buckets need a server-side `file_size_limit`; resizing in the browser is not a safety net.

### Storage Uploads
**Every** `.from("<bucket>").upload(path, file, options)` call must set `cacheControl`. The Supabase Storage SDK auto-prepends `max-age=` to whatever string you pass:

```typescript
// CORRECT — produces wire header `Cache-Control: max-age=31536000, immutable`
.upload(path, file, {
  contentType: detected.mime,
  cacheControl: "31536000, immutable",
  upsert: false,
})

// WRONG — produces `Cache-Control: max-age=public, max-age=31536000, immutable`
//         which browsers + CDNs partially ignore
.upload(path, file, { cacheControl: "public, max-age=31536000, immutable" })

// WRONG — defaults to max-age=3600 (1 hour) → no edge caching
.upload(path, file, { contentType: detected.mime })
```

Note: Supabase serves storage via its own Cloudflare with Bot Management (`Set-Cookie: __cf_bm`), which forces `Cache-Control: no-cache` on the wire even when metadata is correct. Browsers still benefit (304 revalidation), but for true 1-year edge cache an own Worker proxy is required.

### Database
- **Renames do not update function bodies.** Postgres stores PL/pgSQL/SQL bodies as text; after renaming a table or column, search `pg_proc.prosrc` for the old name and fix the functions in the same migration (see `20260926133055_kw_fix_kitchen_rename_in_functions`: 28 functions still used `motorhomes` and blocked dealer approval).
- **Outbox channels:** `kw_outbox.channel = 'market'` is processed by `kw-market-worker` (`kw_enqueue`), `'order'` by `kw-order-worker` (`kw_enqueue_order`). A new event type must be handled by the worker of its channel, otherwise it retries and then stays unprocessed.
- `profiles.role` does NOT exist – roles ALWAYS via `user_roles` table
- `search_path` must be set correctly in all functions (security)
- `SECURITY INVOKER` is the default for new functions. Use `SECURITY DEFINER` ONLY when:
  - The function must bypass RLS by design (cron-triggered batch jobs, mass aggregations, admin RPCs)
  - It's called from an Edge Function that already verified caller identity
  - When using DEFINER: explicitly set `SET search_path = public, pg_catalog` AND add a comment explaining why DEFINER is needed
- New tables: do NOT add to `supabase_realtime` publication by default. Only add if a frontend component will subscribe. Removing later requires a migration; not adding costs nothing.

### Realtime
- Pattern for live updates: Edge Function returns ID + data → Frontend optimistic update → Realtime dedup via ID-Set (ref) → Auto-cleanup after timeout
- Listener-Hygiene: every `supabase.channel(...)` MUST be filtered server-side (`filter: "column=eq.value"` or `=in.(...)`). Global listeners (no filter) cause every WAL change in that table to push to every connected client → exponential cost.
- Periodic Refetch via `setInterval` + `window.addEventListener("focus")` is preferable to Realtime for browse pages (e.g. `/dashboard/projekte`). Realtime is for detail pages where users expect live updates.

## Hosting, Routing & SEO
- nginx serves a **route allowlist** (`docker/default.conf`): unknown paths get a real 404, old URLs of the forked platform (`/verkaufen`, `/auktion/*`, `/wertrechner` …) a 301 (query strings such as UTM/gclid are kept); the SPA has no routes for them. **A new public route must be added to the allowlist**, otherwise it returns 404 in production. Indexable routes also belong in `scripts/prerender.mjs` (`ROUTES`) and in the `sitemap` function.
- Public routes are prerendered during the Docker build (`dist/<route>/index.html`, SPA shell in `dist/spa.html`). If Chromium or a route fails, the build falls back to the plain SPA.
- **Landing-page speed (Lighthouse mobile as in PageSpeed Insights: `/formular`, `/funnel/c`, `/kuechenrechner` 99, LCP ≈ 2.0 s; `/` 96):** on prerendered pages the app bundle starts only after the first contentful paint: `scripts/prerender.mjs` (via `scripts/defer-app-start.mjs`) moves the entry script and all `modulepreload` links into `data-entry`/`data-preload` of `public/js/app-boot.js` at the end of `<body>`, which injects them after the paint event (fallback 3 s, e.g. background tabs). Otherwise ~300 KB of JavaScript share the connection with the render-blocking CSS and the first paint comes seconds later on slow mobile networks. `spa.html` keeps the direct bundle. No synchronous script in `<head>`: `consent-bootstrap.js` sits at the end of `<body>` right before `tracking-loader.js` (keep that order, consent defaults before any Google tag). Hero images above the fold need `srcSet`/`sizes` (`BRAND_IMAGES.kitchen*SrcSet`: phones load 800/1200 px instead of 1600 px). The prerendered HTML must stay visible until React has the route. `main.tsx` mounts only after the first paint and `RouteFallback` shows the captured HTML inside `[data-kw-route]` as Suspense fallback on the first load (`src/lib/initialRouteHtml.ts`); keep that wrapper around `<Routes>`. Fonts: Fira Sans latin only, weights 400/600/800 preloaded, `font-display: optional` (vite.config.ts), otherwise React's re-render of text drawn in the fallback font counts as a later, larger LCP. Small helpers shared with admin libraries (clsx, tailwind-merge, cva, fast-equals) live in `vendor-utils`; `scripts/check-entry-chunks.mjs` (part of `npm run build`) fails if `vendor-recharts` or `vendor-editor` hang statically on the entry again. Late-appearing overlays (cookie banner) must not contain one text block larger than a page's H1, or LCP moves to them. Measure against production with Lighthouse mobile in the default simulated mode (what PageSpeed Insights reports; it counts every request started before the paint) and with `--throttling-method=devtools`, plus a `largest-contentful-paint` PerformanceObserver: a second, later LCP entry for the same text means the swap re-renders it larger.
- Security headers live in `docker/security-headers.conf` and must be included in every nginx block with its own `add_header`. The CSP allows no inline scripts: bootstrap code lives in `public/js/consent-bootstrap.js` and `public/js/tracking-loader.js`. Check changes with `node scripts/check-csp.mjs`.
- `/projekt` and `/abmelden` are served with `no-referrer`, `noindex` and `no-store`; `/admin` and `/dashboard` with `noindex`. The service worker (`public/sw.js`, bump `CACHE_VERSION` on SW changes) does not cache private pages.
- nginx takes the client IP from `CF-Connecting-IP` for Cloudflare ranges (`docker/nginx.conf`); keep the ranges current.

- **Bidding ladder:** since 2026-09-29 (operator decision, Google's recommendation once tracking works) `angebote`, `planer`, `kosten` and `wettbewerber` bid with `MAXIMIZE_CONVERSIONS` without a target on „Küchenanfrage“; the brand campaign keeps 95 % absolute top, max 1 €. Smart Bidding needs about two weeks to learn and ignores CPC ceilings, so spend per click can swing at first; the daily budgets cap it. Add `targetCpaEur` only after a stable CPL (≥ 30 conversions in 30 days). Phase 2, once ≥ ~30 published requests per month arrive: set `QUALIFIED_LEADS_PRIMARY = true` in `kw-google-ads/setup.ts` and run `setup` („Anfrage veröffentlicht“ becomes primary, „Küchenanfrage“ secondary), so bidding learns from checked requests instead of every form fill. Phase 3, once ≥ ~30 revenue events per month arrive: set `OFFLINE_ACTIONS_PRIMARY = true` and run `setup` (the earlier stages become secondary), then bid on conversion value (Maximize Conversion Value, later tROAS; `campaign-settings` has no value strategies yet). Search terms arrive weekly by mail (see weekly search-term report); add negatives and keywords to the plan. PMax/Demand Gen, broad match or AI Max only once conversion volume is solid.

- **Remarketing lists (since 2026-09-29):** `KW_ADS_PLAN.remarketingLists` defines rule-based lists from Google tag page views (URL contains): all visitors (540 days), planner, form and KüchenRechner visitors without a request (90 days, excluded once `/funnel/danke`, the thank-you page of all funnels, was reached) and request sent (540 days). `campaigns` creates missing lists (own mutate before `main`, Google has no temporary IDs for user lists; `validate` therefore checks the links only once the lists exist), updates rules that differ from the plan and attaches every list in observation to the campaigns with `observeAudiences`. One page per rule operand, alternatives as several operands with `OR` (several rule groups in one operand: `TOO_MANY`). The duration sits on each operand as `lookback_window_days`: Google ignores `membership_life_span` for rule-based lists. The name prefix „KüchenWert | " is the key: other lists are never touched; lists renamed or dropped in the plan are detached from the campaigns. The Ads tag sends page views (`send_page_view: true` in `tracking-loader.js`, SPA changes via `analyticsService.ts`) and loads only with marketing consent; the privacy policy describes remarketing (migration `kw_datenschutz_remarketing`). Search uses a list for targeting or bid adjustments only from 1,000 active users; observation and Smart Bidding signals need no minimum.
- **Value feedback (offline conversions):** for leads with a Google click ID, three stages go to Google. „Anfrage veröffentlicht" (category qualified lead): the tender is published (Funnel A/C automatically after the bot check, Funnel B by the admin) and reported only after 24 h without rejection, value = contact price of the tender (fallback `kw_marketplace_settings.contact_price_fallback_cents`), order ID `kw-lead-<lead id>-published`, retracted once the lead becomes `disqualified` or `disputed`. Then every marketplace invoice with its net amount (`lead_purchase` → „Kontakt freigeschaltet", `lead_commission` → „Auftrag vergeben", both category converted lead), so Google learns which clicks bring revenue, not just form fills. `setup` also makes the account goal (category + origin) of the primary stage biddable and keeps call goals out of bidding. Queue `kw_gads_conversion_uploads` (one row per request or invoice in `source_id`, only references and amounts; service role only), filled by `kw_gads_collect_conversions()` and sent by `kw-google-ads` `{ "action": "upload-conversions", "dryRun"? }` (cron `kw-gads-conversion-uploads`, hourly at :25, calls the function only when rows are due). Click IDs and contact data are read fresh from `leads` at upload time, so erasure and anonymization stop uploads. Order ID `kw-inv-<invoice id>` dedupes; cancelled (`status = 'cancelled'`) or refunded (`payment_status = 'refunded'`) invoices are retracted. Retries back off 2 → 24 h, at most 6 attempts, then `rejected`/`retract_failed`. Only invoices within 90 days of the lead (click lookback). Hashed email/phone (Enhanced Conversions for leads) is sent only once the account has accepted the customer data terms and enabled Enhanced Conversions for leads. All three actions are MANY_PER_CLICK (Google rejects ONE_PER_CLICK for gbraid/wbraid) and secondary until their phase. Admin → Tracking shows the counts. `{ "action": "upload-conversions", "probe": true }` sends a made-up conversion and retraction to Google in validate-only mode, without touching the database: expected are per-item errors such as `UNPARSEABLE_GCLID`; `requestAccepted: false` means the request format broke (run it after every `GADS_API_VERSION` bump).
